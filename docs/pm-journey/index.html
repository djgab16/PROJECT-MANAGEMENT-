    Project Charter

    Slide 1 · ~75 sec

    “What did we set out to achieve?”

    Highlight the most important elements. Show how the charter guided the project.

    Vision

    Score every active delivery for breach risk before the deadline passes, and explain each score well enough that a coordinator can act on it.

    In scope

    • • 8-factor explainable risk score, 4 bands
    • • SLA Proactive Monitoring dashboard /sla-monitoring
    • • Background recompute every 30 min
    • • Alert on escalation into Critical
    • • Accuracy measured on recorded outcomes
    • • Logistic-regression challenger in shadow

    Out of scope — deliberately

    • • Any change to delivery CRUD, auth, notifications, activity logging
    • • Paid weather / traffic APIs — conditions come from local history
    • • A calibrated ETA — arrival is directional only
    • • Auto-remediation — the engine recommends, humans act
    • • ML driving operations — shadow only

    Stakeholders & the question each one asks

    Operations Coordinator OP. TEAM
    “Which deliveries are about to breach, and what do I do?”
    Operations Manager ADMIN
    “Is the prediction actually right?”
    IT Administrator
    “Is it stable, audited — and did it break anything?”
    Drivers & Client LZP-001
    Consumers of the workflow that must not regress.
    Capstone Adviser
    Acceptance and academic defensibility.

    Success criteria — testable, not aspirational

    • ✓ Additive-only schema: 3 tables, 3 migrations, 0 drops or renames
    • ✓ Factor weights sum to exactly 1.00 — asserted by unit test
    • ✓ Accuracy computed only from pre-outcome snapshots
    • ✓ Whole controller behind OpTeamAndAbove
    • ✓ Regression baseline recorded at each freeze: 0 build errors, full suite green, tsc exit 0

    Speaker notes

    Spend most of this slide on the Out of scope column — it is the most defensible thing in the charter. Each exclusion was a decision, not an omission: no paid API because factor 8 can be derived from our own history; no calibrated ETA because we never fitted one; ML stays in shadow because a model has to earn promotion. Then land the closing line: "the charter is why the last three slides have so little drama — the boundaries were drawn before we started writing code."

    Scope Changes

    Slide 2 · ~60 sec

    “What changed along the way?”

    Explain why changes were made and how they were managed.

    Approved scope changes with rationale and impact
    # Change Why Impact
    01 WebSockets → HTTP polling Socket layer dropped connections under normal use; reconnect logic kept growing. Simplified. 30 s dashboard refresh, 10 s notifications. Live tracking became reliable.
    02 External conditions API → local history The placeholder formula resolved to a constant — 0.2 on weekdays, 0.533 on weekends. Weighted, a 0.0067 spread. It could never move an order across a band. Factor 8 became real. Route×area×time-bucket history, no paid dependency.
    03 Added a learned risk model Scope said “there is no ML.” A trained challenger was added to answer “could a fitted model do better?” with evidence. Scope grew, risk did not. Shipped Enabled: false, shadow-only.
    04 Single build entry point No solution file existed, and *.sln was git-ignored by the Vite template, so adding one did nothing. One command builds both projects.
    05 Freeze published figures Three known imperfections were found after Week 5 numbers were already cited in documentation. Documented in-code, not silently corrected. See slide 5.

    How change was controlled

    Two-tier gate. Low-risk refactors proceeded; anything touching a published figure or model semantics required an explicit decision.

    Feature branches + PR. feat/at-risk-prediction-sla-monitoring merged via PR #2; feat/learned-risk-model followed.

    Written decision log. Open questions recorded with options, never resolved unilaterally.

    Speaker notes

    Change 02 is the strongest story here — you found a factor that looked like it was working and proved arithmetically that it could not affect any outcome. Quote the 0.0067 figure; it shows you audited your own model rather than trusting it. On change 03, get ahead of the obvious challenge: "yes, this contradicts our earlier documentation that said there is no ML — that document was accurate when written, and we have flagged the inconsistency rather than quietly leaving it."     Risk Management

    Slide 4 · ~80 sec

    “What could have gone wrong, and how did we prevent it?”

    Show the top 3–5 risks and how they were addressed.

    R1 · CRITICAL

    Breaking the system we were told not to touch

    Risk: an enhancement that regresses delivery CRUD, auth or logging fails the whole capstone, not just the feature.

    Control: additive-only migrations; the ML service injected as an optional dependency; the pre-existing test suite kept unchanged so a green run is evidence no existing score moved.

    R2 · CRITICAL

    Measuring ourselves dishonestly

    Risk: the completed-orders view derives its risk fields from the outcome. Scoring accuracy against it returns 100% by construction — a number that is both flawless and worthless.

    Control: a separate outcomes table snapshots the prediction as it stood before the result was known, copied verbatim and never recomputed. Recomputing time-based factors after delivery would leak the answer into its own inputs.

    R3 · HIGH

    Overclaiming the AI in a defence

    Risk: calling a rule-based scorer “AI” is the fastest way to lose credibility under questioning.

    Control: the learned model writes only to separate nullable columns and ships disabled; the dashboard, the alerts and the summary all still read the rule-based score. A written claims-to-avoid table sits alongside the demo script.

    R4 · HIGH

    Training on data that cannot support a model

    Risk: too few rows to identify 8 coefficients, or a dataset that is all breaches or all successes — where the model just learns to say one word forever.

    Control: four training guards. Refuse on single-class data, refuse below a hard row floor, drop out-of-range rows rather than clamp them, reject non-finite input up front. Failures report the reason to the operator instead of quietly fitting garbage.

    R5 · MEDIUM

    Automation misbehaving unattended

    Risk: a background scorer can hot-spin on a bad config value, queue overlapping runs, or die silently on one bad record.

    Control: a hard minimum interval floor regardless of config, a run gate that skips an overlapping tick rather than queueing it, and error handling inside the loop so one failure cannot kill the service.

    Speaker notes

    R2 is your best slide in the entire deck — land it slowly. The line to deliver: "we could have reported 100% accuracy, truthfully computed, and it would have meant nothing." Explaining why you rejected the flattering number is worth more than any metric you could show. If you are short on time, compress R5 to a single sentence and protect R2 and R4.

    Challenges Faced

    Slide 5 · ~80 sec

    “What obstacles did we face?”

    Be honest about struggles and how you solved them.

    A factor that did nothing

    Problem: the operating-conditions factor had hardcoded traffic and weather values. It resolved to one of two constants, a weighted spread of 0.0067 — mathematically incapable of changing any risk band.

    Fix: rebuilt it from our own delivery history, bucketed by route, area and time of day, with a six-level fallback chain so a brand-new route still gets a defensible number.

    Alert fatigue by design

    Problem: the scorer runs every 30 minutes. Naively, every run re-alerted on every Critical order — the same delivery would page the floor 48 times a day.

    Fix: read the previous risk level before overwriting it, and alert only on the transition into Critical. One alert per escalation, not one per refresh.

    Tests that failed on weekends

    Problem: the conditions factor reads the calendar, so scores differed depending on which day the suite ran. A test suite that passes Monday and fails Saturday is worse than no suite.

    Fix: pin that factor to a fixed value in the test harness, and test the factor itself separately with explicit dates.

    Weights that would not sum to one

    Problem: the assertion that our 8 weights total 1.00 failed. Values like 0.35 and 0.03 are not exactly representable in binary floating point.

    Fix: compare with rounding rather than exact equality. The test still catches a real broken weight table — which matters, because a bad sum silently de-calibrates every band.

    Reads that dragged image payloads

    Problem: summary queries materialised every column on the order — including two unbounded base64 proof-of-delivery images per row.

    Fix: narrow projections and no-tracking reads on every path, and batch pre-fetching so the scoring loop performs no database work at all.

    Our own documentation went stale

    Problem: the Week 5 write-up stated plainly “there is no ML.” True when written — then we added a learned model, and the two documents disagreed.

    Fix: an explicit consistency warning in the demo script naming the contradiction, and narration phrased so the rule-based engine remains the system of record.

    Still open — and we say so

    The breach counter mixes archived and active scope. The predicted-arrival column uses hand-picked offsets, not a fitted ETA. The risk score can never actually reach 1.00 — its real ceiling is about 0.99. All three are documented in the source rather than quietly patched, because the affected figures were already published.

    Speaker notes

    Pick three to narrate — the dead factor, the alert storm, the weekend test failures — and let the panel read the rest. Then deliver the Still open box deliberately, out loud. Volunteering three unfixed defects, with the reason they stayed unfixed, is the single most disarming thing you can do in a defence; it also pre-empts the exact questions an examiner would otherwise use to catch you out.

    The “No Touch” Rule

    Slide 6 · ~70 sec

    “How did we ensure we didn't touch Capstone 1?”

    Show how you enforced the rule.

    1 · Additive schema only

    Three new tables via three migrations. Nothing dropped, nothing renamed, no existing column changed meaning. The original schema replays clean from empty.

    2 · Mostly new surface

    One new page, one new controller, one new service layer. Where existing files had to change, the change was declared rather than absorbed — see the integration points below.

    3 · Reuse, don't replace

    Alerts go into the existing notification feed and the existing activity log, rather than a parallel system competing with them.

    4 · Off by default

    The learned model ships disabled. Installing the build changes nothing on its own — it has to be switched on deliberately.

    5 · Shadow isolation

    Model output lands in separate nullable columns. The three fields the dashboard, alerts and summary actually read are never written by it.

    6 · Optional dependency

    The prediction engine can be constructed without the ML service at all — so the original path stays independently testable.

    7 · Access unchanged

    The whole feature sits behind the existing role policy. Drivers and clients are blocked at both the route and the API — demonstrable live.

    8 · Frozen figures

    Published numbers are reproduced verbatim. Known imperfections are documented in-code rather than corrected mid-defence.

    9 · The evidence

    The pre-existing tests are unchanged and still green — 66 of them at feature freeze. Not an assurance; a re-runnable check that no original behaviour moved.

    Where we did change Capstone 1 — four declared integration points

    “No touch” did not mean zero edits. It meant no undeclared edits. Four places had to change, and each one is defensible on its own terms:

    • Outcome capture hooks — the order service and controller call outcome capture when a delivery reaches a terminal status. Without this the accuracy matrix would stay permanently empty. Three separate hook sites were needed because two code paths set status directly instead of going through the central update method.
    • Registration wiring — the data context and startup file register the new tables and services. Unavoidable in any additive feature.
    • Two existing behaviours corrected — analytics average delivery time was a hardcoded 3.5 and now computes from completed orders; the seeder was changed to migrate rather than drop and recreate, with the destructive path gated to Development. Both are improvements to Capstone 1, and both are still changes to it.
    • One existing migration was edited — its unconditional column drops were made conditional, because a clean database could not migrate at all: it failed on a column that no longer gets created. Applied databases are unaffected, since an applied migration never re-runs. Disclosed here because it is the one place we modified Capstone 1's migration history.

    What we did not have — stated plainly

    There was no read-only database user and no separate environment. One connection string, one local database, one configuration file, trusted connection with full rights. Compliance was enforced by code and schema discipline, not by infrastructure — additive-only migrations, shadow columns, a feature switched off by default, and the original test suite as the tripwire.

    That is a weaker guarantee than an isolated environment, and we would take a read-only replica and a second configuration profile if we ran this again. Saying so is cheaper than being asked.

    Speaker notes

    Run the nine boxes fast — "three ways we constrained the code, three ways we constrained the risk, three ways we proved it" — then slow right down for the last two panels, because that is where the marks are. Volunteer the four integration points before anyone asks. The framing that survives questioning is "no touch meant no undeclared edits, and here are all four edits."

    The examiner's prompt explicitly suggests a read-only user and a separate environment, and we had neither. Do not skate past that — say it, say what we used instead, and say what we would do differently. A disclosed limitation costs you a fraction of what a discovered one does. If you have the recording, cut to the green test run here rather than describing it.
